# TraceBox — план реализации

**Цель:** получить рабочую и демонстрируемую первую версию за один вечер.  
**Ориентир:** 5–7 часов чистой работы. Если время заканчивается, сокращать объём по разделу «Приоритеты при нехватке времени», а не растягивать Core.  
**Правило:** после каждого этапа приложение должно оставаться запускаемым. Не начинать Advanced-функции, пока весь Core не работает.

## Этап 0. Каркас и запуск

**Результат:** минимальное PyQt6-приложение открывает главное окно.

- Создать модули из `ARCHITECTURE.md`.
- Настроить `main.py`, `QApplication`, `MainWindow`.
- Добавить `assets/tracebox.svg`.
- Сделать простой `README.md` с запуском из `.venv`.

**Готово, когда:** `python main.py` открывает окно без traceback.

## Этап 1. SQLite и репозитории

**Результат:** схема БД создаётся автоматически, данные сохраняются между запусками.

- Реализовать `connect_database` и `initialize_database`.
- Создать четыре таблицы и индексы из `ARCHITECTURE.md`.
- Реализовать CRUD соревнований и заданий, затем заметок и артефактов.
- Проверить внешние ключи и каскадное удаление.

**Готово, когда:** тесты репозиториев проходят на временной БД; удаление соревнования не оставляет дочерних записей.

## Этап 2. Базовые инструменты

**Результат:** функции анализа работают независимо от GUI.

- Реализовать потоковое хеширование MD5/SHA-1/SHA-256 за один проход.
- Реализовать Base64, Hex и URL encode/decode.
- Написать тесты успешных и ошибочных сценариев.

**Готово, когда:** `pytest tests/test_tools.py` проходит.

## Этап 3. Основной интерфейс и CRUD

**Результат:** пользователь управляет соревнованиями и заданиями через GUI.

- Добавить вкладки «Обзор», «Соревнования», «Задания», «Инструменты».
- Реализовать диалоги соревнования и задания.
- Реализовать таблицы, обновление данных, фильтр по соревнованию/статусу.
- Подключить подтверждение удаления.

**Готово, когда:** соревнование и задание можно создать, изменить, просмотреть и удалить через интерфейс; данные сохраняются после перезапуска.

## Этап 4. Заметки, артефакты и обзор

**Результат:** карточка задания хранит рабочие материалы.

- Добавить диалог подробностей задания с вкладками описания, заметок и файлов.
- Реализовать CRUD заметок.
- Добавить выбор файла, вычисление SHA-256 и сохранение метаданных.
- Добавить проверку доступности пути без удаления записи.
- Подключить счётчики и прогресс на Dashboard.

**Готово, когда:** можно добавить заметку и артефакт к заданию; удаление записи об артефакте не удаляет исходный файл; обзор обновляется.

## Этап 5. Инструменты, экспорт и полная проверка

**Результат:** закрыты основные сценарии Core.

- Подключить GUI к хешированию и кодировщикам.
- Добавить копирование результата.
- Реализовать CSV и TXT экспорт выбранного соревнования.
- Прогнать все тесты и вручную пройти пользовательские сценарии.
- Исправить только найденные дефекты; не начинать большой рефакторинг.

**Готово, когда:** FR-01—FR-08 из `TECHNICAL_SPEC.md` выполнены, `pytest` проходит, приложение не теряет данные при обычном использовании.

## Этап 6. Сдача

**Результат:** репозиторий готов к демонстрации и передаче преподавателю.

- Проверить `.gitignore` и отсутствие пользовательской БД/секретов.
- Обновить README: назначение, возможности, запуск, зависимости, структура.
- Создать Git-коммит после проверки `git diff` и `git status`.
- Настроить сборку Windows EXE на Windows runner GitHub Actions либо выполнить её на Windows.
- Проверить exe на чистой Windows-среде, если она доступна.
- Подготовить короткую пояснительную записку и презентацию по реальной реализации.

**Готово, когда:** исходники, инструкции и материалы сдачи соответствуют фактическому состоянию приложения.

## Приоритеты при нехватке времени

### Нельзя вырезать

1. Запуск приложения.
2. SQLite с четырьмя таблицами и связями.
3. CRUD соревнований и заданий.
4. Хотя бы по одному рабочему сценарию заметок и артефактов.
5. Хеширование и кодировщики.
6. Экспорт CSV/TXT.
7. Тесты инструментов и репозиториев.

### Можно упростить

- Dashboard: сначала только счётчики и прогресс, без графиков.
- Фильтры: только соревнование и статус.
- Дизайн: аккуратная тёмная тема без сложных анимаций и кастомных виджетов.
- Артефакты: только один файл за раз, без копирования в хранилище.
- TXT-отчёт: простой читаемый шаблон.

### Исключить до завершения Core

Hex Viewer, анализ строк, извлечение метаданных, сравнение файлов, теги, плагины, сетевые функции, встроенный AI, фоновые задачи без подтверждённой необходимости.

## Работа с Kilo Code

- **Architect** вызывается только для конкретного архитектурного вопроса или изменения требований; не просить повторно пересказывать уже готовые документы.
- **Code** — основной агент реализации. Один запрос = один законченный этап или небольшая задача с явно названными файлами и критериями приёмки.
- **Reviewer** вызывается на контрольных точках: после слоя БД, после основного GUI и перед сдачей. Не запускать ревью после каждой мелкой правки.
- Передавать агенту только нужные файлы/фрагменты; не прикладывать весь проект к каждому запросу.
- Любое заявление агента о тестах проверять по фактически выполненной команде.
- Не разрешать агенту делать `git commit`, `git push`, `git reset` или `git clean` без отдельного явного согласия.

## Первая команда после подготовки документов

Попросить Code выполнить только этап 0. Пусть он перечислит создаваемые файлы, создаст минимальный запускаемый каркас и проверит `python main.py`. Не просить его одновременно реализовать БД, все вкладки и инструменты.
