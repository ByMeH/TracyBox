# TraceBox — архитектура

**Версия:** 1.0  
**Принцип:** минимальное разделение GUI, доступа к данным и чистых инструментов.

## 1. Структура проекта

```text
TraceBox/
├── main.py
├── constants.py
├── database.py
├── repositories.py
├── tools.py
├── reports.py
├── dialogs.py
├── main_window.py
├── assets/
│   └── tracebox.svg
├── tests/
│   ├── test_tools.py
│   ├── test_repositories.py
│   └── test_reports.py
├── docs/
├── requirements.txt
├── README.md
├── AGENTS.md
└── .gitignore
```

Не нужно создавать отдельные пакеты, базовые классы или универсальные менеджеры, пока реальная сложность этого не требует.

## 2. Ответственность модулей

### `main.py`

- Создаёт `QApplication`.
- Получает путь к пользовательскому каталогу приложения и создаёт его.
- Открывает соединение с БД и вызывает инициализацию схемы.
- Создаёт `MainWindow`, передавая ему соединение.
- При завершении закрывает соединение.
- Возвращает код завершения Qt-приложения.

### `constants.py`

Содержит списки статусов и сложностей для `QComboBox`, подписи вкладок и другие действительно общие значения. Значения статусов и сложностей должны совпадать с `CHECK`-ограничениями в `database.py`. Не превращать файл в хранилище каждого строкового литерала.

### `database.py`

Публичные функции:

- `connect_database(db_path) -> sqlite3.Connection` — создаёт соединение, включает `sqlite3.Row` и `PRAGMA foreign_keys = ON`.
- `initialize_database(connection) -> None` — создаёт таблицы и индексы через `CREATE TABLE IF NOT EXISTS`.

Соединение создаётся один раз при старте приложения и передаётся в главное окно и функции репозиториев. В тестах путь задаётся через `tmp_path` либо используется отдельное соединение `:memory:`. Не использовать глобальное соединение.

### `repositories.py`

Содержит функции чтения и изменения данных. Каждая функция получает `sqlite3.Connection` первым аргументом. SQL не размещается в обработчиках GUI.

Основные группы функций:

- соревнования: `get_competitions`, `add_competition`, `update_competition`, `delete_competition`;
- задания: `get_challenges`, `get_challenge`, `add_challenge`, `update_challenge`, `delete_challenge`;
- заметки: `get_notes`, `add_note`, `update_note`, `delete_note`;
- артефакты: `get_artifacts`, `add_artifact`, `delete_artifact`;
- обзор: `get_dashboard_stats`, `get_recent_challenges`.

Названия можно уточнить при реализации, но не нужно строить универсальный CRUD-фреймворк. Записи возвращаются как `sqlite3.Row` или простые значения с предсказуемой структурой.

Каждая операция записи должна завершаться commit; при ошибке транзакция должна откатываться. Для одиночного `INSERT`/`UPDATE` достаточно контекстного менеджера соединения. Связанные операции выполнять в одной транзакции. Функции `update_challenge` и `update_note` явно устанавливают `updated_at = CURRENT_TIMESTAMP`, потому что SQLite не обновляет это поле автоматически.

Функции `update_*` и `delete_*` возвращают `True`, если затронута хотя бы одна строка, и `False`, если записи с таким идентификатором нет. `update_competition` и `update_challenge` выполняют полную замену записи: все изменяемые поля — обязательные аргументы, и частичный вызов невозможен; пустая строка в аргументе означает намеренную очистку поля.

### `tools.py`

Чистые функции без зависимости от Qt и БД:

- `calculate_file_hashes(path) -> dict[str, str]`;
- `encode_base64(text)`, `decode_base64(text)`;
- `encode_hex(text)`, `decode_hex(text)`;
- `encode_url(text)`, `decode_url(text)`.

Хеширование читает файл блоками по 1 МиБ и обновляет MD5, SHA-1 и SHA-256 за один проход. Функция не меняет файл. Ошибки чтения и преобразования не следует скрывать; GUI преобразует ожидаемые исключения в понятные сообщения. Декодер Base64 перед декодированием удаляет ASCII-пробельные символы (пробел, табуляция, переводы строки), но не исправляет отсутствующий padding.

### `reports.py`

Функции экспорта принимают данные/соединение и путь назначения. Модуль не открывает диалоги и не зависит от Qt. CSV формируется через `csv` с `encoding="utf-8-sig"` и `delimiter=";"`; TXT — обычным UTF-8.

### `dialogs.py`

Содержит диалоги ввода:

- `CompetitionDialog` — создание/изменение соревнования;
- `ChallengeDialog` — создание/изменение задания;
- `NoteDialog` — создание/изменение заметки;
- `ChallengeDetailsDialog` — описание задания, список заметок и артефактов, действия над ними.

Диалог отвечает за поля, проверку ввода и возврат введённых значений. Он не должен самостоятельно выполнять SQL.

### `main_window.py`

`MainWindow(QMainWindow)` собирает вкладки «Обзор», «Соревнования», «Задания», «Инструменты», подключает сигналы к коротким обработчикам, вызывает репозитории и обновляет таблицы/счётчики.

Обработчик кнопки не должен содержать сложный SQL или алгоритм хеширования. Повторяющееся обновление таблиц можно вынести в небольшие методы класса.

## 3. Модель SQLite

Все таблицы используют `INTEGER PRIMARY KEY`. Даты и время хранятся в ISO 8601 текстом. Для отметок времени по умолчанию используется `CURRENT_TIMESTAMP`.

### `competitions`

| Поле | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | INTEGER | PK | Идентификатор |
| `name` | TEXT | NOT NULL, CHECK(trim(name) <> '') | Название |
| `platform` | TEXT | NOT NULL DEFAULT '' | Организатор/платформа |
| `url` | TEXT | NOT NULL DEFAULT '' | Ссылка |
| `start_date` | TEXT | NOT NULL DEFAULT '' | Дата начала ISO `YYYY-MM-DD` или пустая строка |
| `description` | TEXT | NOT NULL DEFAULT '' | Описание |
| `created_at` | TEXT | NOT NULL DEFAULT CURRENT_TIMESTAMP | Дата создания |

### `challenges`

| Поле | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | INTEGER | PK | Идентификатор |
| `competition_id` | INTEGER | NOT NULL, FK → competitions(id) ON DELETE CASCADE | Соревнование |
| `title` | TEXT | NOT NULL, CHECK(trim(title) <> '') | Название задания |
| `category` | TEXT | NOT NULL DEFAULT '' | Категория свободным текстом |
| `difficulty` | TEXT | NOT NULL DEFAULT 'Средняя', CHECK из трёх значений | Сложность |
| `status` | TEXT | NOT NULL DEFAULT 'Новое', CHECK из четырёх значений | Статус |
| `points` | INTEGER | NOT NULL DEFAULT 0, CHECK(points >= 0) | Баллы |
| `description` | TEXT | NOT NULL DEFAULT '' | Условие/описание |
| `created_at` | TEXT | NOT NULL DEFAULT CURRENT_TIMESTAMP | Дата создания |
| `updated_at` | TEXT | NOT NULL DEFAULT CURRENT_TIMESTAMP | Дата изменения |

Допустимые `difficulty`: `Лёгкая`, `Средняя`, `Сложная`.  
Допустимые `status`: `Новое`, `В работе`, `Решено`, `Пропущено`.

### `notes`

| Поле | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | INTEGER | PK | Идентификатор |
| `challenge_id` | INTEGER | NOT NULL, FK → challenges(id) ON DELETE CASCADE | Задание |
| `title` | TEXT | NOT NULL, CHECK(trim(title) <> '') | Заголовок |
| `content` | TEXT | NOT NULL, CHECK(trim(content) <> '') | Текст |
| `created_at` | TEXT | NOT NULL DEFAULT CURRENT_TIMESTAMP | Создано |
| `updated_at` | TEXT | NOT NULL DEFAULT CURRENT_TIMESTAMP | Изменено |

### `artifacts`

| Поле | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | INTEGER | PK | Идентификатор |
| `challenge_id` | INTEGER | NOT NULL, FK → challenges(id) ON DELETE CASCADE | Задание |
| `path` | TEXT | NOT NULL | Путь к исходному файлу |
| `file_name` | TEXT | NOT NULL | Имя файла на момент добавления |
| `file_size` | INTEGER | NOT NULL, CHECK(file_size >= 0) | Размер в байтах |
| `sha256` | TEXT | NOT NULL, CHECK(length(sha256) = 64) | SHA-256 |
| `added_at` | TEXT | NOT NULL DEFAULT CURRENT_TIMESTAMP | Дата добавления |

Индексы: `challenges(competition_id)`, `challenges(status)`, `notes(challenge_id)`, `artifacts(challenge_id)`. Индексы добавляются только для колонок, по которым действительно выполняется фильтрация или соединение.

## 4. Правила связей и удаления

```text
competitions 1 ─── N challenges
challenges  1 ─── N notes
challenges  1 ─── N artifacts
```

- У задания ровно одно соревнование.
- При удалении соревнования SQLite каскадно удаляет его задания, заметки и записи об артефактах.
- При удалении задания удаляются его заметки и записи об артефактах.
- При удалении заметки удаляется только эта заметка.
- При удалении артефакта удаляется только запись в БД, не файл.
- Перед удалением соревнования GUI показывает подтверждение с предупреждением о связанных записях.

## 5. Основные сценарии и поток данных

### Создание соревнования

`MainWindow` открывает `CompetitionDialog` → диалог возвращает проверенные значения → `repositories.add_competition` записывает их → главное окно обновляет таблицу и обзор.

### Создание задания

`MainWindow` открывает `ChallengeDialog` со списком соревнований → пользователь заполняет поля → репозиторий сохраняет запись → обновляются таблица заданий, фильтры и обзор.

### Добавление артефакта

`ChallengeDetailsDialog` вызывает `QFileDialog` → `tools.calculate_file_hashes` вычисляет хеш и размер → `repositories.add_artifact` сохраняет метаданные. Если чтение не удалось, запись не создаётся.

### Экспорт

GUI предлагает выбрать соревнование и путь сохранения → репозиторий получает необходимые данные → `reports.py` пишет файл → GUI показывает результат.

## 6. Обработка ошибок

- `sqlite3.Error` перехватывается на границе GUI-операции; пользователю показывается краткое сообщение, подробности остаются в терминальном traceback при разработке.
- `OSError` при чтении файла не должен приводить к неполной записи артефакта.
- `binascii.Error`, `ValueError` и `UnicodeDecodeError` при декодировании обрабатываются как некорректный ввод.
- Не использовать `except Exception` для сокрытия неизвестных ошибок.
- Не закрывать приложение из-за ошибки одной операции, если состояние данных остаётся согласованным.

## 7. Путь к БД и жизненный цикл

По умолчанию БД хранится в `Path.home() / ".tracebox" / "tracebox.db"`. Каталог создаётся при старте. В тестах функция подключения принимает временный путь. Файл БД, WAL/SHM-файлы и пользовательские данные исключаются из Git.

Для MVP отдельная система миграций не нужна. Схема создаётся через `CREATE TABLE IF NOT EXISTS`. До выпуска первой версии любые изменения схемы проверяются на новой пустой БД; не обещать совместимость с будущими версиями без миграций.

## 8. Тестируемые границы

- `tools.py` тестируется без Qt.
- `repositories.py` тестируется на временной SQLite-БД.
- `reports.py` тестируется на временном каталоге и проверке содержимого файлов.
- GUI проверяется вручную по сценариям из `TECHNICAL_SPEC.md`; тестировать каждый виджет автотестом для MVP не требуется.

## 9. Решения, которые не следует усложнять

- Репозитории — функции, а не иерархия классов.
- Одна SQLite connection на время работы приложения; она явно передаётся нужным функциям.
- Никакого ORM.
- Никакого контейнера зависимостей, event bus или плагинной системы.
- Не выносить каждую вкладку и каждую кнопку в отдельный модуль.
- Не добавлять QThread заранее. Сначала проверить, заметно ли блокирует интерфейс реальный сценарий.
